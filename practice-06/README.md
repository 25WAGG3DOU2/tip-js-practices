# 3. Реализация

## 3.1. HTTP-клиент

`api-client.js` поддерживает методы GET, POST, PATCH и DELETE. Для тела используется `JSON.stringify` и заголовок `Content-Type: application/json`. Ответ 204 преобразуется в `null` без попытки разобрать JSON. Тайм-аут реализован через `AbortSignal.timeout`, внешняя отмена — через `AbortSignal.any` с внешним `AbortController`. Ошибки классифицируются по `kind`: `http`, `network`, `invalid-response`, `timeout`, `aborted`.

## 3.2. Доменный API

`task-api.js` реализует `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`, `createTask`, `updateTask`, `setTaskCompleted`, `deleteTask`, `resetDemoData`. Схема ответа проверяется функциями `isTask` и `isCategory` до передачи в интерфейс. Коллекции проверяются на уникальность id и соответствие `meta.total` длине `data`.

## 3.3. Состояния интерфейса

Переходы состояний:

- `loading` — при старте и при каждой новой загрузке фильтров;
- `ready` — список задач отображён;
- `empty` — сервер вернул пустой список, старые карточки удалены;
- `error` — сеть или сервер недоступны, показывается кнопка повтора.

При ошибке `setListState("error", ...)` выставляет `aria-busy="false"` и показывает `#retry-load`. Повторная загрузка (`#retry-load`, `#refresh-list`) вызывает `controller.refresh()`, который либо повторяет начальную загрузку, либо перезапрашивает список с текущими фильтрами.

## 3.4. Изменение данных

После создания, редактирования, смены статуса и удаления контроллер вызывает `reloadCurrent()` для повторного запроса списка с текущими фильтрами. Это гарантирует, что данные на экране совпадают с сервером: `createTask` возвращает назначенный сервером id, `setTaskCompleted` и `updateTask` — актуальную запись, `deleteTask` — `null` (204). Кнопки действий блокируются на время мутации через `setMutationPending(true/false)`.

## 3.5. Защита от устаревшего ответа

Перед новым запросом предыдущий отменяется через `AbortController`: `beginRequest()` вызывает `abortInflight()` и создаёт новый контроллер. Контроллер также хранит `lastRequestId` и сравнивает его после `await` — если ответ пришёл от устаревшего запроса, он игнорируется. Ошибки с `kind: "aborted"` не показываются пользователю.

# 4. Индивидуальный вариант

Начальный фильтр: `{ priority: "medium" }` (вариант 4)

Индивидуальный сценарий: при открытии `http://127.0.0.1:5506/?dataset=variant` приложение применяет фильтр `priority=medium` и запрашивает `/api/tasks?priority=medium`. В списке отображаются задачи с id [1, 10, 19, 28], `#task-total = 4`. Создание, редактирование и удаление работают с этим фильтром: после мутации список перезапрашивается с тем же `priority=medium`, поэтому новые задачи с другим приоритетом не появляются, а изменённые на другой приоритет — исчезают из выборки.

## 6. Ответы на контрольные вопросы

**Почему `fetch` не отклоняет Promise при ответе 404?**

404 — это успешный HTTP-ответ от доступного сервера. `fetch` отклоняется только при сетевой ошибке, неверной схеме URL или отмене. Поэтому после `await fetch` нужна явная проверка `response.ok`.

**Почему ответ 204 нельзя разбирать вызовом `response.json()`?**

У 204 нет тела. `response.json()` бросит `SyntaxError`. Клиент проверяет `response.status === 204` и возвращает `null` до чтения тела.

**Чем состояние `empty` отличается от `error`?**

`empty` — успешный ответ сервера с пустым списком; данные получены, фильтр ничего не нашёл. `error` — сбой запроса: сеть, тайм-аут, неверный ответ или HTTP-ошибка. В `empty` нет кнопки повтора, в `error` она есть.

**Зачем отменять предыдущий запрос при смене фильтров?**

Чтобы медленный предыдущий ответ не перезаписал интерфейс новыми данными. `AbortController.abort()` отменяет запрос, а `lastRequestId` дополнительно отбрасывает ответ, если он всё же пришёл.

**Почему после мутации список повторно запрашивается у API?**

Чтобы интерфейс показывал только то, что реально сохранено на сервере: сервер назначает `id` при создании, может нормализовать поля, применяет текущие фильтры и порядок. Локальное обновление массива разошлось бы с сервером.
