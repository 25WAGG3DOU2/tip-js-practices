# Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A → B → C → D → E → F | A и B и C — синхронный код и начало async-функции до await. D — микрозадача Promise.resolve().then. E — продолжение async после await null (тоже микрозадача). F — задача таймера. |
| Фактический результат | A → B → C → D → E → F | A — первый console.log. B — начало demonstrateAwait до await. C — последний синхронный console.log. D — микрозадача Promise. E — продолжение async-функции после await. F — таймер с задержкой 0 выполнится только после всех микрозадач. |

**Синхронный код:** A, B, C.

**Микрозадачи:** D (обработчик `Promise.resolve().then`) и E (продолжение после `await null`).

Таймер с задержкой 0 не выполняется немедленно: он ставится в очередь задач, которая обрабатывается после всех микрозадач.

Если удалить один обработчик Promise (D), порядок станет A → B → C → E → F. Если удалить `await null` (E), порядок станет A → B → C → D → F. Сами микрозадачи между собой выполняются в порядке регистрации.

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Готовый учебный HTTP API: маршруты, фильтры, CORS, отладочные ответы. Изменять не нужно. |
| `src/api-client.js` | `buildUrl` и `createApiClient`: формирование URL, GET, Accept, тайм-аут, внешняя отмена, проверка `Response.ok` и `Content-Type`, разбор JSON, `ApiError` с `kind`. |
| `src/task-api.js` | `createTaskApi`: маршруты `/tasks`, `/tasks/:id`, `/categories`, нормализация фильтров, проверка схемы задач и категорий, `Promise.all`. |
| `src/variant.js` | Номер варианта и фильтры. |
| `src/main.js` | Консольный сценарий: `loadInitialData`, таблица задач, контрольная ошибка 404. |

`fetchFn` передаётся аргументом, чтобы модульные проверки работали без сети. HTTP-ошибки (`response.ok === false`) отличаются от сетевых (`fetch` отклонился): при HTTP сервер доступен и вернул структурированный ответ, при сети ответа нет вовсе. JSON после разбора проверяется по контракту, потому что синтаксически корректный ответ может не совпадать со схемой задачи, категории или коллекции.

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id [1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34] |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id [4, 13, 34] |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | `[{ id: 1, name: "Учёба" }, { id: 2, name: "Проект" }, { id: 3, name: "Организация" }]` |
| `loadInitialData({ completed: false, priority: "high" })` | `{ tasks: [3 задачи], categories: [3 категории], meta: { total: 3, filters: { completed: false, priority: "high", categoryId: null, q: "" } } }` |

Правила проверки:

- задача: `id` и `categoryId` — положительные безопасные целые; `title` — непустая строка до 100 символов после `trim`; `completed` — boolean; `priority` — `low | medium | high`;
- категория: `id` — положительное безопасное целое; `name` — непустая строка до 100 символов;
- уникальность `id` проверяется в коллекциях задач и категорий;
- `meta.total` равен длине `data` для коллекции задач.

## Последовательная и параллельная загрузка

Замеры на локальном API через `/debug/delay?ms=150`, три запуска для каждой схемы.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---|---|---|---|
| Два последовательных `await` | ~300 | ~300 | ~300 | Две задержки по 150 мс складываются. |
| `Promise.all` | ~150 | ~150 | ~150 | Задержки перекрываются, общее время — примерно одна задержка. |

Причина: `Promise.all` не создаёт параллельность, но позволяет двум независимым `fetch` находиться в полёте одновременно. Последовательный вариант ждёт завершения первого запроса до старта второго. Точные миллисекунды зависят от машины и не сравниваются с чужими.

## Вывод

Реализованы buildUrl, createApiClient, createTaskApi и вариант 4. Проверки: API 18/18, клиент 26/26, интеграция 13/13. Порядок очередей подтверждён: A → B → C → D → E → F (синхронный код → микрозадачи → таймер). Разведены шесть видов результата: успех, http, network, invalid-response, timeout, aborted. HTTP-ошибки — по response.ok и телу; сетевые — по отклонению fetch; формат — по Content-Type и схеме. Тайм-аут и отмена — через AbortSignal.timeout и AbortSignal.any (различаются по kind). Promise.all запускает оба запроса до общего await, сокращая время до примерно одной задержки.
